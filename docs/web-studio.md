# Browser version (beta)

`apps/studio-web` lets people record and edit without installing anything. It is part of the landing site, one deploy and one address: `web.yml` builds it into the site's `app/` folder (`apps/web/dist/app`), and the header, hero and a landing section link to it. `pnpm dev:site` runs both locally the same way: the landing dev server proxies `/app/` to the app's dev server, which serves under that base. It needs Chrome or Edge on a computer; other browsers and phones see a card that points to the desktop app.

The web shell is a product page on a still, dark background image (`src/assets/web-background.webp`: faint contour lines on neutral graphite with a soft blue light at the upper right; the globe is the landing page's alone), laid out wide (header and studio up to 1600 px, hero up to 1560 px): the promise and proof chips beside a live sample (`ResultPreview.tsx`: the real frame painter on the "ocean" wave background, close to a macOS wallpaper, a pointer path whose pauses become focus events through the same `pointerEvents()` rules as a recording, and the core camera zooming to them, with the resulting zooms on a timeline; a still zoomed frame under reduced motion) with the compact recorder card right under it (both audio toggles on one row, their hints as tooltips and screen-reader text; stacked where the column is too narrow), so recording starts from the first screen without scrolling (in one column the recorder comes before the sample); below them a three-step strip and a comparison with the desktop app. Live recording shows a timer and a big Stop, preparation shows progress, and the studio appears below with a summary header and a local-tab callout. The accent is Apple's system blue (`#0a84ff`, `#0071e3` for filled buttons) instead of the desktop app's violet, also in the shared studio, on neutral grey surfaces. The interface uses single flat colours only, no gradients or glossy highlights, and small corner radii (8 px buttons, 8–12 px cards; no pill buttons, also in the shared studio); the studio's restyling is scoped under `html.web`, so the desktop app is unchanged, and only the video background presets users pick keep their gradients. The header is a slim full-width translucent bar with one hairline below, its content aligned with the hero: the "ScreenSway Web" wordmark on the left; on the right the landing page's `LanguageToggle` (EN and VI side by side, the current one lit) and, after a hairline, the desktop-app link as a quiet outlined button, so "Start recording" stays the page's only filled call to action. The sample's pointer is the shared pointing hand (`apps/desktop/src/HandPointer.tsx`), also used by the landing page's browser section. Links between the app and the landing page stay in the same tab with a short cross-fade (a cross-document view transition declared inline in both `index.html` files); an unexported recording still asks before leaving.

## What it reuses

The studio is the desktop one. `src/main.tsx` renders the desktop `I18nProvider`, styles and `RecordingStudio` (preview, styles, backgrounds, frames, timeline, trim, zoom editing, export button). `vite.config.ts` aliases `@tauri-apps/api/core` and `@tauri-apps/api/event` to `src/tauri/`, so the studio's commands are answered in the browser by `src/backend.ts`, and it defines `__SCREENSWAY_WEB__`, which sets `isWeb` in `apps/desktop/src/platform.ts`. With `isWeb`:

- the preview does not draw a cursor or click ripples, because the real pointer is already in the video;
- the captions, privacy (redaction), shortcut-key, brand, chapters and GIF/copy controls and "Show in Finder" are hidden (there is no camera file, and browsers do not report keys); middle cuts, undo/redo, filled 9:16 frames and export presets work as on the desktop;
- export results show the file's frame rate; "Download again" appears only for downloaded exports (see Export);
- `enWeb`/`viWeb` in `i18n.tsx` replace wording about the Mac, clicks and folders. New `web.*` strings live there too; keep English and Vietnamese in sync.
- unsupported browsers and phones get a full-screen alternative instead of a half-rendered recorder.

Edits and background images stay in memory for the tab. While recording, MediaRecorder's chunks are written to a file in the browser's private storage (OPFS, `recordings/`), so a long Retina recording does not fill memory; a window without that storage (some private windows) is told so instead of recording into memory; the file is deleted when the recording is closed, and files older than 12 hours (closed tabs, crashes) when the next recording starts. If a write fails (the disk is full) the recording stops, the incomplete file is deleted and the page says why; stopping sharing while the app is still starting cancels the start. Leaving the page asks first until the recording has been exported (`beforeunload`).

## Recording

`src/recorder.ts` asks for the microphone first, then `getDisplayMedia` (screen, window or tab; full resolution up to 3840 × 2400, 30 fps, `cursor: "always"`). Zooms magnify the recording, so it is recorded at `width × height × 30 × 0.15` bits per second (8–40 Mbps, about 27 Mbps for a 3024 × 1964 Retina screen); at camera bitrates text turned blocky once zoomed. If the start fails at any step, every track, the audio graph and the worker are released. Audio from the shared surface and the microphone are mixed by Web Audio into one track. The video goes through `fixedSize()` first: MediaRecorder keeps writing frames of a resized window into an MP4 that declares the first size, which no decoder can read, so frames of another size are fitted into the first size with black bars (same-size frames pass untouched). `MediaRecorder` writes MP4 (H.264 High 5.1/AAC) when the browser supports it, otherwise WebM. The page requires `MediaStreamTrackProcessor`, `MediaStreamTrackGenerator`, `OffscreenCanvas` and WebCodecs. Chromium can share the sound of a tab, and of the whole computer on Windows; on macOS only tab audio is available.

## Following the pointer

Browsers never say where the pointer is or when it clicks. A clone of the video track is read with `MediaStreamTrackProcessor` in a worker (`src/pointer/worker.ts`), which keeps running while the tab is in the background. Frames are analysed at most 1600 px wide (copied with `VideoFrame.copyTo` into one reused buffer; the e2e checks the worker analyses at least 80% of 30 fps) by `PointerTracker` (`src/pointer/tracker.ts`):

1. It compares each frame with the previous one and groups the changed pixels.
2. When two small changes look like "the pointer left here and arrived there" (the new place shows what the old place showed a frame earlier), the arrived shape is a candidate template. Shape, color and size are learned, so custom pointer colors, hands and I-beams all work.
3. A shape is trusted only after a chain of three such moves, each starting where the last one ended. Animated content (video, wallpapers, spinners) changes in small pairs too, but stays in place.
4. Trusted shapes are searched for where the frame changed, nearest to the last position first. When nothing changes around the pointer it is still there; when it is lost, one band of the frame is searched per frame.

The frames' timestamps start at zero on their own clock, not at the recording's first frame. The worker also records how much each frame changed (on 64 × 40 copies), and after recording the first 20 s of the file are compared the same way; the offset with the best correlation (±2 s, kept when it is at least 0.5) moves the pointer onto the recording's timeline (`src/pointer/align.ts`).

`src/pointer/focus.ts` turns the positions into the studio's pointer events: `move` events, plus a `focus` event wherever the pointer settles for 0.8 s after travelling 12% of the width. Focus events start zooms like clicks do (`generateZoomSegments` treats every non-move event the same). While zoomed, `buildCameraTrack` moves the camera to each new focus that is not already near the centre, starting slightly early like a zoom; clicks keep the desktop behaviour, where merged clicks only pan when the pointer leaves the dead zone. On the test recordings these settings zoom about half the time (instead of three quarters with 0.5 s and 8%) and keep the pointer in view 99.8% of the zoomed time, more than 10% away from the edges 87% of it.

Measured on a real 35 s recording (Retina, animated Edge wallpaper) with the real pointer path drawn back in, after the first lock (under 1 s): 95–98% of frames within 2% of the width, median error 2 px, for arrow, hand and I-beam pointers; ~3 ms per frame in a worker. Clicks cannot be inferred reliably (about half found, many false), which is why zooms follow stops instead. Focus zooms covered all but 1 s of the zoomed time click zooms would have, plus about 13 s more; people remove extra zooms on the timeline.

## Export

`src/exporter.ts` is loaded on first use. It checks that the browser can encode the chosen size, decodes the recording with mediabunny (`1.60.0`, pinned) and paints each frame with the desktop helper's layout and camera plan (the studio's base layer, then the zoomed crop inside the rounded video area; the browser's `drawImage` scaling is not the helper's Lanczos filter), encodes H.264 with WebCodecs at the desktop exporter's bitrate (`width × height × fps × 0.12`, 8–100 Mbps) and muxes MP4 with the trimmed audio (AAC, or Opus where AAC is unavailable; gaps are filled with silence so sound stays in sync). Middle cuts arrive as `sourceTimesMs` and `sourceRanges`: each frame is read at its source time and the kept audio ranges are laid end to end. The browser first asks where to save (`showSaveFilePicker`) and the MP4 is streamed straight to that file, with no "Download again". Without the dialog it is streamed to the browser's private storage (`exports/`) and downloaded from that file; only that latest file is kept, for "Download again", and a cancelled or failed one is deleted. Exports are never built in memory: with neither available, exporting reports that the browser cannot save files. Browsers keep a file's old content until its writable stream is closed, and mediabunny closes the stream on cancel too, so the exporter writes through `transactional()`: a cancelled or failed export (including a failed write, or a cancel while the last step at 99% runs) discards its writes and leaves a chosen file exactly as it was; a chosen file is never deleted. Committing the file is the point of no return: from then on the progress shows 100%, Cancel is no longer offered (on the web only; the desktop helper reports 100% before it finalizes and adds the sound, and stays cancellable) and a late cancel is ignored, so the export reports what happened to the file. Export errors from the browser backend are message keys (`web.export*`) that the studio translates (`isMessageKey`), so they follow the page's language. It runs faster than real time. Captions are not offered on the web yet.

## Known beta limits

- Pointer accuracy was measured on one real Retina capture (95–98% of frames within 2% of the width, see above), drawn back into its video; it is not part of CI because that recording shows a private screen. Real screen sharing, cursor themes and other scaling factors have only been checked by hand.
- Writes that fail after part of an export was written are covered only by failing the first write: mediabunny writes 16 MB at a time and the e2e exports are shorter.
- Long recordings (10 minutes on Retina) have not been soak-tested; recordings and exports stream to disk, so memory should stay flat.

## Privacy

Feedback and statistics: the header has a "Send feedback" button and the export panel another, both opening the shared feedback form, which posts to the analytics API's `/v1/feedback` from `backend.ts`. A footer switch, off by default, lets the visitor be recognised on return visits (a random ID in `localStorage`, see `src/identity.ts`); without it, the only ID is the tab's journey in `sessionStorage`. Under Do Not Track or Global Privacy Control nothing is sent or stored and the switch and the feature card are hidden. Details: `docs/analytics.md`.

Production builds carry a Content-Security-Policy `<meta>` (`scripts/vite-csp.mjs`, configured in `vite.config.ts`): scripts, styles, fonts and workers only from the site (plus `blob:` workers and media, `data:`/`blob:` images and Vite's inlined `data:` fonts), and `connect-src` limited to the analytics origin plus `data:`/`blob:` (the exporter decodes an image from a `data:` URL), so even injected code could not send a recording anywhere. `test:e2e` runs every scenario against the built page and fails on any CSP violation. No recording content is uploaded. The page sends anonymous, cookieless usage counts (source `studio`, see `docs/analytics.md`) when built with `VITE_ANALYTICS_URL`, honouring Do Not Track and Global Privacy Control: `src/analytics.ts` counts visits, unsupported browsers, recording starts, finishes and failures and clicks to the desktop app, and `backend.ts` answers the shared studio's `track_event` with the same sender (exports, styles); `telemetry_status` still reports the desktop opt-in as unavailable, so no settings switch appears.

## Validation

`pnpm --filter @screensway/studio-web typecheck`, `pnpm --filter @screensway/studio-web test` (tracker on synthetic frames, focus detection, timeline alignment) and `pnpm build:studio-web`. `pnpm --filter @screensway/studio-web test:e2e` builds the app and drives Edge (`BROWSER=chrome` for Chrome) through recording with sound, a mid-recording resize, stopping from the browser's controls, export to a file (read back and checked with mediabunny), cancelling a 4K export at 60% and while its file is being completed (99%, with slowed writes), exports failing before writing, while writing and while committing, each leaving an existing chosen file's content untouched, the commit point (slowed close: Cancel gone, the file replaced), deleting the stored recording on close, stopping sharing while starting, a full disk while recording and while committing the recording, a file that refuses to open, explained in Vietnamese, a 1.2 s recording trimmed at both ends (the export must last exactly the kept part, with sound and picture ending together), a middle cut left out of picture and sound, and a failed start that must release the screen. It replaces the shared screen with an animated canvas whose pointer sits on whole pixels like a real one. For other experiments without a screen-sharing prompt, replace `navigator.mediaDevices.getDisplayMedia` in a test page with `captureStream()` of a video that contains a pointer, and drive Edge with Playwright (`--use-fake-device-for-media-stream` for the microphone); this exercises recording, the worker, the studio and export end to end. Pointer accuracy can be scored against a ScreenSway recording's `pointer-events.json` drawn back into its video with ffmpeg.
